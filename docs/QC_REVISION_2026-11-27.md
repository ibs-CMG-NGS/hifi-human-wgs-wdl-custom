## 1. 무엇이 왜 틀렸나

QC 리포트 생성기가 control 지표와 P1 을 **원시 파일에서 직접 계산**하고
있었는데, 장비(SMRT Link)가 같은 값을 이미 계산해 둔 것과 **단위가 달랐습니다.**

| 지표 | 기존 계산 | 문제 | 올바른 출처 |
|---|---|---|---|
| Control Read Length | `sequencing_control.subreads.bam` SEQ 길이 평균 | control 템플릿 **1회 통과(subread) 길이**(23–49 kb)를 쟀다. 기준 `≥50 kb` 는 **polymerase read length**(ZMW 전체 합, 실측 45–92 kb) 다 | `statistics/<movie>.reports.zip` → `control.report.json` → `readlength_mean` |
| Control Read Count | 같은 BAM 의 레코드 수 | **subread 개수**(수천)를 셌다. 기준 `≥500` 은 ZMW 기준 수다 | 같은 파일 → `reads_n` |
| P1 (ZMW Productivity) | `ccs_report.json` 로 추정 | 근사치다. 코드 주석도 그렇게 적어 두었다 — *"exact P1 requires SMRT Link instrument metrics"*. 실측과 최대 **+16%p** 차이 | `loading.report.json` → `productivity_0/1/2_n` |
| Control Read Concordance | **측정하지 않았다** | 문서가 `mean·mode 모두 ≥88%` 를 요구하는데 리포트에 항목이 없었다 | `control.report.json` → `concordance_mean` / `concordance_mode` |

### 영향의 방향

- **Control Read Length — 허위 경보였습니다.** 28샘플 전부 WARNING 이었는데,
  제대로 재면 **27/28 PASS** 입니다. "장비·소모품 성능 저하" 로 읽힐 수 있는
  경보가 전량 오보였습니다.
- **P1 — 실제 신호를 가리고 있었습니다.** 근사치로는 28/28 PASS 였으나
  실측은 **7 PASS / 21 WARNING** 입니다. 과거 run 들이 문서 최적구간
  (50–70%) 을 넘는 70.5–78.4% 로 적재되어 있었습니다.

두 방향이 반대라 종합 판정은 거의 움직이지 않았지만, **판정의 근거가 완전히
교체되었습니다.**

## 2. 기준(임계값) 변경 사항

측정 버그와 별개로, 기준의 근거를 문서와 맞췄습니다. **완화한 칸은 하나뿐입니다.**

| 지표 | 기존 | 개정 | 근거 |
|---|---|---|---|
| Missing Adapter | PASS <5% / WARN 5–10% / FAIL ≥10% | **PASS ≤10% / WARN >10%** | 문서는 `should ideally be <10%` 한 줄만 말한다. 5% 칸은 근거가 없었다. 28샘플 실측 **0.60–4.50%** 로 양쪽 기준 모두 통과하여 **판정 결과는 불변**이다. 단 최대값 4.50% 가 구 5% 선에 바로 붙어 있었다 — 조금만 높았다면 근거 없는 WARNING 이 발생할 상태였다 |
| Control Concordance | 없음 | **PASS ≥88% / WARN <88%** | 문서 `mean & mode are typically ≥88%`. 신설 |
| Est. Coverage | **임계값 없음** | **PASS ≥35× / WARN 25–35× / FAIL <25×** | **내부 기준** (§5 주의) |
| Read Length mean | PASS ≥15 kb | **변경 없음** | 문서 15–20 kb 행. 정상 작동 중 |
| HiFi Yield | PASS ≥100 Gb | **변경 없음** | 문서 15–20 kb 행 100–120 Gb |

적용 스펙 행을 **15–20 kb 라이브러리**로 확정했습니다. 리포트의 "24-hr movie
time 기준" 표기는 사실과 달랐습니다 — 자체 6개 run 은 **모두 30 hr**
(`MovieLength = 1800.0` 분) 입니다. 문서 스펙 표는 15–20 kb 를 24 hr 과,
30 hr 을 20–25 kb 와 짝지어 **우리 조건과 일치하는 행이 없습니다.** 긴 movie 는
yield·read length 에 유리하므로 15–20 kb 행을 쓰는 것은 보수적인 선택이며,
리포트에 그 사실을 명시했습니다.

또한 리포트에 **임계값마다 출처(문서 / 내부)를 표기**하는 열을 추가했습니다.
제조사 문서가 말하지 않는 칸을 문서 기준인 척 두면 이번과 같은 오진이
반복됩니다.

## 5. 판정을 그대로 쓸 때의 주의 — 범위 제한

LIMS 가 자체 기준 없이 본 리포트의 판정을 사용한다고 들었으므로, 판정이
**어디까지 유효한지** 명시합니다.

### 5.1 출처가 둘입니다

리포트 기준표의 "기준 출처" 열을 보십시오.

- **문서** — PacBio `103-604-700 (SMRT Link Run Details report overview,
  Revio v13.3)`. 종·분석 종류와 무관하게 적용됩니다.
- **내부** — `Est. Coverage` **한 항목뿐**입니다.

### 5.2 Est. Coverage 판정은 마우스 TG 분석 전용입니다

`PASS ≥35× / WARNING 25–35× / FAIL <25×` 는 **마우스(2.7 Gb)에서 transgene
통합 접합을 검출하는 데 필요한 깊이**에서 나왔습니다 — 납품 분석이 35.3–39.3×
였고, TG-6283 의 오른쪽 접합이 37.2× 에서 지지 리드 ~1개였습니다.

**다른 종이나 다른 분석 목적에는 적용하지 마십시오.** 제조사 문서는 사람
유전체 15–20 kb 라이브러리의 기대 coverage 를 20× 로 적고 있어, 35× 를 사람
샘플에 적용하면 근거 없는 경고가 발생합니다.

그래서 생성기에 `--coverage-thresholds PASS,WARN` 옵션을 추가했습니다.
`none` 을 주면 coverage 는 **값만 표시되고 판정은 N/A** 로 나옵니다.
사람 샘플 리포트는 이 모드로 생성해야 합니다.

`FAIL (<25×)` 선은 자체 28샘플에 해당 사례가 없어 **아직 실증되지 않은
경계**입니다.

### 5.3 판정이 없는 진단 지표 두 개

`Declared Insert (kb)` 와 `RL / Insert (%)` 는 **의도적으로 판정이 없습니다.**
LIMS 에서 합불로 변환하지 마십시오.

실측 HiFi read length 는 랩이 입력한 insert 크기보다 **항상** 작습니다 —
자체 28웰 전수에서 예외 0건, 비율 62.4–83.6%(중위수 74.0%). 이 비율은 run
안에서 2–4%p 로 모이고 run 사이에서 72% 대 82% 로 갈리는 **prep 배치의
성질**이어서, 샘플별 합불 선을 그으면 배치 차이를 샘플 경고로 잘못
보고하게 됩니다.

용도는 **Read Length 경고의 원인 분리**입니다 — 비율이 정상(≈75% 이상)인데
Read Length 가 낮으면 라이브러리가 아니라 목표 insert 가 낮았던 것입니다.

## 6. 보류 항목 — LIMS·랩 확인 필요

### 6.1 `r84285_20260108_080127` + `r84285_20260113_075724` 리포트는 재생성하지 않았습니다

이 리포트(사람 샘플 8웰)는 **샘플명이 장비 metadata 와 일치하지 않아** 보류
했습니다. 재생성하면 어느 이름을 쓸지 정해야 하고, 그 선택이 LIMS 기록의
샘플 귀속을 바꾸므로 임의로 결정하지 않았습니다.

- `r84285_20260113_075724` 의 **5웰 전부**에서 기존 리포트의 샘플명이 장비
  metadata 의 `WellSample Name` 보다 **한 칸 뒤로 밀려** 있습니다. 즉 각 웰에
  **다음 샘플의 이름**이 붙어 있습니다.
- `r84285_20260108_080127` 의 3웰은 두 기록이 **서로 다른 명명 체계**입니다
  (장비: 영문이니셜+번호 코드 / 리포트: 번호+성명). 기존 리포트에만 있는
  이름 1개, 장비 metadata 에만 있는 코드 3개가 존재합니다.
- 참고로 마우스 5개 run 은 양쪽 이름이 일치합니다. 단 `20260219 / 1_B01` 은
  장비 metadata 가 `6238`, 리포트가 `TG-6283` 입니다 — 하위 분석 전체가
  `TG-6283` 을 사용했고 그것이 올바른 계통명이므로, **장비 metadata 쪽이
  오타**입니다. 즉 장비 metadata 도 무조건 정답은 아닙니다.

**필요한 결정:** 두 run 의 웰↔샘플 귀속을 무엇으로 확정할지 (의뢰서/접수
기록 등 제3의 근거 권장). 확정되면 `--coverage-thresholds none`,
`--genome-size 3.1` 로 재생성하겠습니다.

**그 전에 LIMS 가 확인할 것:** 이 8샘플의 QC 기록이 **올바른 샘플에 귀속되어
있는지.** 샘플명이 어긋난 채 등록되었을 가능성이 있습니다.

### 6.2 사람 샘플의 coverage 기준

사람 WGS 의 분석 요구 깊이가 정해지면 `--coverage-thresholds` 로 지정할 수
있습니다. 미정 상태에서는 `none` (판정 없음) 이 맞습니다.
